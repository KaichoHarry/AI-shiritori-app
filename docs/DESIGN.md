- 作成日: 2026-07-20(改訂)
- 対象: Claude Code (CLI) による実装を想定した技術設計書

## 0. この文書の位置づけ

本書は要件をもとにした設計書。実装を進める中でClaude Codeが技術的な詳細(ライブラリ選定、細かいAPI形状など)を補って良い。ただし「1. 前提・要確定事項」に挙げた項目は仕様のブレに直結するため、実装前にユーザーへ確認するか、本書内の暫定案に従って実装し、コメントで暫定である旨を残すこと。

### v0.3での主な変更点

- パスワード再設定方式を「ユーザーがメール内トークンで自ら新パスワードを設定する」方式から、「管理者へメール通知→管理者が空メール返信で承認→システムが新パスワードを自動生成してユーザーへメール送信する」管理者承認フローに変更(1章・6.2節・7.1節参照)。
- メール送受信は開発初期から実接続(SMTP送信 + IMAPポーリングによる返信検知)で実装する。

### v0.2での主な変更点

- モード1・モード2に「単語の辞書存在チェック」を追加。存在しない単語は即ゲームオーバーにせず、エラーメッセージを返して同じターンで再入力させる仕様に変更。
- モード3を単語しりとりではなく「文章しりとり(日常会話を紡ぎながら、文の最後の音で次の文を始める)」モードとして再定義。
- 画面構成を全面見直し。ログイン→(新規登録 / パスワード再設定)→ダッシュボード(3モード・設定・履歴への導線)というフローを追加。
- 設定画面(モード2のデフォルト難易度、モード3の会話トーン)を新設。

## 1. 前提・要確定事項(暫定案あり)

要件が曖昧だった以下の点は、暫定案を採用した上で実装を進める。変更したい場合はここを直せば設計全体に反映できるよう、極力ロジックを一箇所(しりとり判定モジュール)に集約する。

| 項目 | 暫定案 |
|---|---|
| 判定の基準 | 単語/文章は「読み仮名(ひらがな)」で判定する。入力はひらがな/カタカナ/漢字混在を許容し、判定前にひらがな正規化する(4章参照) |
| 長音「ー」の扱い | 末尾が「ー」の場合、直前の母音音を使って次の頭文字とする(例: 「コーヒー」→「ひ」) |
| 小さい文字(っ・ゃ・ゅ・ょ等) | 拗音(ゃ・ゅ・ょ)は直前の文字と結合した1音として扱う。促音「っ」は拗音とは別物とし、結合せず独立した1モーラとして扱う(例: 「ごりら」→「らっぱ」は成立する。ユーザー確認済み) |
| 「ん」で終わる | 即ゲームオーバー・チェーン終了(要件通り。モード1/2/3共通) |
| 単語/文章の重複使用 | 同一セッション内で使用済みの単語(モード1/2)を再度使用したらゲームオーバー。モード3では文章単位の完全一致チェックは仕組みとして残すが、発生頻度は低い想定 |
| 単語の実在チェック(辞書照合) | モード1・モード2で導入。辞書に存在しない単語が入力された場合は**ゲームオーバーにはせず**、「この言葉は辞書に存在しないようです」等のエラーメッセージを返し、同じターンのまま再入力を促す(6章・9章参照) |
| モード2でAIが辞書にない語を返した場合 | AI側の生成失敗として扱い、プレイヤーの勝利とする(AIは辞書チェックに落ちても再生成のチャンスを与えず、その場で敗北扱いとする暫定案) |
| モード3の性質 | 単語単位のしりとりではなく、日常会話の「文章」を紡ぎながら、直前の文章の最後の音から次の文章を始める「文章しりとり」。辞書照合は行わない(自然文が対象のため) |
| AI対戦モードの勝敗条件 | AIが「んで終わる」「同じ単語を出す」「辞書にない語を出す」「一定時間内に単語を生成できない」のいずれかに該当した場合、プレイヤーの勝利としてゲーム終了 |
| 難易度 | 「AIがわざと間違えたり考えつかなかったりする確率」と「Gemini APIのtemperature/候補語彙の難易度」の2軸で調整する(5章参照)。設定画面でデフォルト値を保持し、ゲーム開始時に上書き可能とする |
| 認証方式 | メールアドレス+パスワードによる自前実装(JWT)を暫定案とする。Google等のOAuthは将来拡張 |
| パスワード再設定方式 | ユーザーが直接新パスワードを設定するトークン方式ではなく、**管理者承認フロー**を採用する: (1)ユーザーが再設定を申請すると、管理者宛にそのユーザーのメールアドレスと申請IDを含む通知メールを送信する (2)管理者は内容を確認し、そのメールに**本文を空にして返信**することで承認する (3)バックエンドが管理者メールボックスをIMAPで定期的にポーリングし、件名・スレッド情報から該当の申請を特定、本文が空であることを確認する (4)確認できたらランダムな新パスワードを自動生成してハッシュ化保存し、ユーザー登録済みのメールアドレスへ新パスワードを送信する。セキュリティ上の弱点(メール返信の詐称可能性、二要素認証なし等)は許容した上での簡易実装であり、詳細な設計判断・今後の改善案はrepo-root/README.mdに記載する |
| フリートーク(文章しりとり)モードの終了条件 | 「ん」で終わる文章が出た場合に終了。加えてユーザーが任意のタイミングで「終了する」操作で終了できる。明確な勝敗はつけない |
| 管理者のメールアドレス | 環境変数(`ADMIN_EMAIL`)で管理する。UIやリポジトリに直書きしない |
| メール送受信の実装状態 | 開発初期段階から実接続で実装する。送信はSMTP、管理者からの返信検知はIMAPポーリングを用いる。認証情報は`.env`(Git管理外)で管理する |
| 辞書データソース | 具体的な辞書データ(ローカル辞書 or 外部辞書API)の選定はClaude Codeに委ねる。4.3節に方針を記載 |

## 2. 機能要件

### 2.1 モード1: ソロプレイ(一人しりとり)

- ユーザーが単語を入力 → システムが「お尻の文字」を抽出 → ユーザーが次の単語を入力、を繰り返す。
- UIには直前に入力された単語(またはそのお尻の文字)のみを表示し、それより前の履歴は原則非表示とする(要件の「前に入力した文字だけが見える」仕様)。ただし裏側では全履歴をDBに保存し、ゲーム終了後の振り返り・過去ログ閲覧では全履歴を表示する。
- 単語を入力すると、以下の順でチェックする(詳細は8章)。
  1. 辞書に存在する単語か → 存在しない場合は**ゲームオーバーにせず**エラーメッセージを表示し、同じターンで再入力させる
  2. 「ん」で終わっていないか → 終わっていればゲームオーバー
  3. 直前の単語の最後の音とつながっているか → つながっていなければゲームオーバー
  4. そのセッション内で使用済みの単語でないか → 使用済みならゲームオーバー
- ゲームオーバー時: 経過ターン数・使用単語一覧をまとめた結果画面を表示し、DBにセッション結果を保存する。

### 2.2 モード2: AI対戦モード

- プレイヤーが単語を入力 → バックエンドが2.1と同じ判定(辞書存在チェックを含む)を行う → 辞書に無い語ならエラーを返して再入力させ、通過すればGemini APIへ問い合わせてAIの単語を生成させる → その単語を画面に表示 → プレイヤーが次の単語を入力、を繰り返す。
- 難易度設定(易しい/普通/難しい、または数値スライダー)は設定画面でデフォルト値を選べる他、ゲーム開始時にも変更可能。難易度に応じて以下を変化させる。
  - AIがわざと失敗する確率(例: 難易度「易しい」は20%の確率でAIが「思いつかなかった」判定になる)
  - Geminiへのプロンプトの制約(例: 難易度「難しい」は難読語・長い単語を優先させる指示を追加)
  - 応答のtemperatureや候補語彙の傾向
- 終了条件:
  - プレイヤー側が「ん」で終わる/重複語を出す → プレイヤーの負け(辞書にない語の場合は負けにせず再入力させる)
  - AI側が「ん」で終わる語しか出せない/重複語を出す/辞書に存在しない語を返す/一定時間(タイムアウト)内に応答できない/Gemini APIがエラーを返す → プレイヤーの勝ち

### 2.3 モード3: 文章しりとり(フリートーク)モード

要件の再確認により、以下のとおり再定義する。

- 単語単位のしりとりではなく、**文章(1〜数文程度の発言)**を使ったしりとり。ユーザーとAIが日常会話・コント風のノリで文章を紡ぎながら、直前の発言の文末の音から次の発言を始めていく。
- 例: ユーザー「今日は天気がいいね」→(文末の読みは「い」)→ AI「いい天気だと洗濯物がよく乾くよね」→(文末は「く/ね」の処理は4章の正規化ルールに従う)→ ユーザー「ねこも気持ちよさそうに寝てるよ」→ ...
- 単語のような辞書照合は行わない(自然な会話文が対象であり、辞書に載っている/いないという概念がそぐわないため)。
- 終了条件:
  1. いずれかの発言(ユーザー・AIどちらでも)が「ん」の音で終わった場合、そこでチェーンが途切れたとして会話(セッション)を終了する
  2. 完全に同一の文章が繰り返された場合も終了する(想定頻度は低いが仕組みとしては用意する)
  3. 上記に該当しなくても、ユーザーが任意のタイミングで「終了する」操作をすればいつでも終了できる
- 明確な勝敗はつけず、結果は「ended_by_n」「ended_by_duplicate」「ended_by_user」のいずれかとして記録する。
- 会話のトーン(フレンドリー/丁寧/コント風 等)は設定画面でユーザーが選択可能。選択したトーンはGeminiへのシステムプロンプトに反映する(5.2節参照)。

### 2.4 共通機能

- ユーザー登録・ログイン・ログアウト・パスワード再設定(メール経由)
- ログイン後のダッシュボードから3モード・設定・履歴へ遷移
- 設定画面: モード2のデフォルト難易度、モード3の会話トーンを保存・変更できる
- 過去のゲーム(3モード共通)のログ(セッション単位)の一覧・詳細閲覧
- ログイン中ユーザーのみ本編プレイ・ログ閲覧が可能(ゲスト利用は本設計のスコープ外。必要なら別途検討)

## 4. アーキテクチャ概要

```
[ブラウザ]
   │  HTTPS
   ▼
[Next.js フロントエンド]  ── (Next.js API Routes は極力使わず、Goバックエンドに直接リクエストする方針)
   │  REST API (JSON)
   ▼
[Go バックエンド API サーバー]
   │            │             │
   │            │             └── SMTP送信(管理者通知・新パスワード通知)
   │            └── Gemini API (モード2の単語生成・モード3の会話生成)
   ▼
[PostgreSQL]
  - users / user_settings / password_reset_tokens
  - game_sessions
  - game_words (モード1/2) / game_messages (モード3)

[IMAPポーリングワーカー(バックエンドと同一プロセス内 or 別goroutine)]
   - 管理者メールボックスを定期ポーリングし、パスワード再設定申請への
     「空メール返信」を検知してpassword_reset_tokensを照合・確定させる
```

- フロントエンドはSPA的な画面遷移(ログイン→ダッシュボード→各モード→結果→履歴)を持つ。
- しりとりの正誤判定ロジック(辞書存在チェック・お尻の文字抽出・重複チェック・「ん」判定)はバックエンド側に実装し、フロントエンドは表示とユーザー入力の送信のみを担当する(チート防止・ロジック一元化のため)。

### 4.1 かな変換(読み仮名化)

- 漢字/カタカナ→ひらがな読みへの変換は、Go側で形態素解析ライブラリ(例: kagome等、辞書データにIPADIC/UniDic系を使用)を用いる。

### 4.2 辞書存在チェック(モード1・2用)

- 形態素解析ライブラリが単語を「既知語」として解析できるか(未知語処理にフォールバックしていないか)を利用し、実在する単語かどうかを判定する方式を基本方針とする。
- 上記だけで判定精度が不十分な場合は、追加でオープンな日本語辞書データ(例: SudachiDict等の見出し語一覧)との照合や、外部辞書API(国語辞書系API)の利用を検討する。具体的なデータソース・実装方式の最終選定はClaude Codeに委ねる。
- 固有名詞(人名・地名等)を実在語として許容するかどうかは、採用する辞書データの収録範囲に依存する。ここも運用しながら調整可能なように、辞書チェックのロジックは1箇所のモジュールに集約する。

## 5. Gemini API連携仕様

### 5.1 モード2(AI対戦)

- リクエスト時にバックエンドから以下をプロンプトとして渡す:
  - 直前のプレイヤーの単語(お尻の文字)
  - これまで使用済みの単語一覧(重複禁止のため)
  - 難易度パラメータに応じた指示(例: 語彙レベル、わざと間違える確率の反映)
- レスポンスのバリデーション(2.2節の判定を流用):
  1. 返ってきた単語が「お尻の文字」から始まっているか
  2. 「ん」で終わっていないか
  3. 使用済み単語でないか
  4. 辞書に存在する単語か
  5. 上記のいずれかを満たさない場合、または応答が得られない/タイムアウトした場合 → 「AIの敗北(プレイヤーの勝利)」として扱う
- 難易度による確率的な「わざと失敗」もバックエンド側の乱数で制御し、条件を満たした場合はGemini APIを呼ばずに敗北処理をしても良い(コスト削減の観点からも推奨)。

### 5.2 モード3(文章しりとり・フリートーク)

- システムプロンプト例: 「あなたはお笑い芸人のようなノリで、文章しりとり(直前の発言の文末の音から次の発言を始める言葉遊び)を交えながらカジュアルな会話を続けるAIです。単語単位の厳密なしりとりルールではなく、文章のつながりを重視してください。」
- ユーザーが設定画面で選んだ会話トーン(例: フレンドリー/丁寧/コント風)をシステムプロンプトに反映する。
- 直近N件(例: 直近10往復)の会話履歴を都度コンテキストとして渡す。
- AIの応答が「ん」で終わらないよう、また可能な限り正しく文章しりとりが成立するようプロンプトで指示する。ただし、AI応答が「ん」で終わってしまった場合は2.3節の終了条件どおりチェーン終了として扱う(AIの勝敗という概念はない)。
- 明確な終了判定(んで終わる/完全重複)がない限り、ユーザーが「会話を終了する」操作をした時点でセッションを終了しDBに保存する。

### 5.3 API利用上の注意

- Gemini APIキーはバックエンドの環境変数で管理し、フロントエンドには一切露出させない。
- レート制限・タイムアウト・リトライ方針を実装する(例: 5秒タイムアウト、リトライなしでエラー時は即敗北/エラー画面)。

## 6. データベース設計

### 6.1 ER概要

```
users 1 ── * game_sessions 1 ── * game_words (モード1/2)
      │                     1 ── * game_messages (モード3)
      1 ── 1 user_settings
      1 ── * password_reset_requests
```

### 6.2 テーブル定義

#### users

| カラム | 型 | 説明 |
|---|---|---|
| id | UUID (PK) | ユーザーID |
| email | text (unique) | メールアドレス |
| password_hash | text | ハッシュ化済みパスワード |
| display_name | text | 表示名 |
| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 更新日時 |

#### user_settings

| カラム | 型 | 説明 |
|---|---|---|
| user_id | UUID (PK, FK → users.id) | 対象ユーザー |
| mode2_difficulty | text | モード2のデフォルト難易度(`easy` / `normal` / `hard`) |
| mode3_tone | text | モード3のデフォルト会話トーン(`friendly` / `polite` / `comedy` 等、値はClaude Codeが具体化して良い) |
| updated_at | timestamptz | 更新日時 |

#### password_reset_requests

管理者承認フロー(1章参照)における申請の状態を管理するテーブル。ユーザーに払い出すトークンではなく、管理者メールとの照合用の内部識別子として`request_id`を用いる。

| カラム | 型 | 説明 |
|---|---|---|
| id | UUID (PK) | ID (= `request_id`。管理者宛メールの件名等に埋め込み、返信スレッドの照合に使う) |
| user_id | UUID (FK → users.id) | 対象ユーザー |
| status | text | `pending` / `approved` / `expired` |
| admin_notified_at | timestamptz | 管理者への通知メール送信日時 |
| approved_at | timestamptz (nullable) | 管理者の空メール返信を検知した日時 |
| expires_at | timestamptz | 有効期限(期限切れの申請はIMAPポーリング側で無視する) |
| created_at | timestamptz | 申請日時 |

セキュリティ上の設計判断・既知の弱点・今後の改善案(2要素認証化など)は`README.md`に詳細を記載する。

#### game_sessions

| カラム | 型 | 説明 |
|---|---|---|
| id | UUID (PK) | セッションID |
| user_id | UUID (FK → users.id) | プレイヤー |
| mode | text | `solo` / `vs_ai` / `free_talk` |
| difficulty | text (nullable) | `easy` / `normal` / `hard` (モード2のみ) |
| tone | text (nullable) | 会話トーン (モード3のみ) |
| status | text | `in_progress` / `finished` |
| result | text (nullable) | モード1/2: `win` / `lose`。モード3: `ended_by_n` / `ended_by_duplicate` / `ended_by_user` |

### 7.4 モード1・2共通(単語送信)

| メソッド | パス | 説明 |
|---|---|---|
| POST | /api/games/{id}/words | プレイヤーの単語を送信。判定結果(継続/辞書エラーで再入力/ゲームオーバー)を返す。モード2の場合はAI側の応答単語も併せて返す |

レスポンス例(辞書に存在しない単語 = 非致命的エラー、再入力可):

```json
{
  "accepted": false,
  "fatal": false,
  "reason": "word_not_found",
  "message": "「◯◯」という言葉は辞書に見つかりませんでした。別の言葉を入力してください。",
  "status": "in_progress"
}
```

レスポンス例(モード2、正常継続時):

```json
{
  "accepted": true,
  "fatal": false,
  "player_word": { "word": "しりとり", "reading": "しりとり" },
  "ai_word": { "word": "リンゴ", "reading": "りんご" },
  "status": "in_progress"
}
```

レスポンス例(ゲームオーバー = 致命的、そのターンで終了):

```json
{
  "accepted": false,
  "fatal": true,
  "reason": "duplicate_word",
  "status": "finished",
  "result": "lose"
}
```

`reason` の想定値:

| reason | 種別 | 説明 |
|---|---|---|
| `word_not_found` | 非致命的 | 辞書に存在しない単語。再入力させる |
| `ends_with_n` | 致命的 | 「ん」で終わった |
| `duplicate_word` | 致命的 | 使用済み単語の再使用 |
| `connection_mismatch` | 致命的 | 直前の単語とつながらない |
| `ai_word_not_found` | 致命的(AI側) | AIが辞書にない語を生成 → プレイヤーの勝利 |
| `ai_timeout` / `ai_generation_failed` | 致命的(AI側) | AIが応答できなかった → プレイヤーの勝利 |

| メソッド | パス | 説明 |
|---|---|---|
| POST | /api/games/{id}/messages | ユーザーの発言(文章)を送信し、AIの返答を受け取る。「ん」終端・完全重複を検知した場合はstatusをfinishedにして返す |

## 8. しりとり判定ロジック仕様(モード1・2共通モジュール)

判定はバックエンドの単一モジュール(例: `internal/shiritori`)に集約する。

1. 入力語を読み仮名(ひらがな)へ正規化する
2. **辞書存在チェック**: 実在する単語かどうかを判定する。存在しない場合は「非致命的エラー(`word_not_found`)」として即座に返す。この場合、使用済みリストへの追加やターン加算は行わない
3. 「ん」で終わっていないかチェック(終わっていれば致命的: `ends_with_n`)
4. 直前の単語の末尾の音と、入力語の先頭の音が一致するかチェック(長音・拗音の正規化ルールは1章の暫定案に従う。不一致は致命的: `connection_mismatch`)
5. そのセッション内の使用済み単語(reading基準)と重複していないかチェック(重複は致命的: `duplicate_word`)
6. 全て通過すれば「継続」とし、使用済みリストに追加してturn_countを加算する

この関数はモード1(ユーザー同士の連続入力)・モード2(ユーザー入力とAI応答の両方の検証。ただしAI側が辞書エラーになった場合はプレイヤーの勝利として扱う点が異なる)で共通利用する。

## 8.1 文章しりとり判定ロジック仕様(モード3専用モジュール)

1. 発言(文章)を読み仮名へ正規化し、末尾の句読点・記号を除去したうえで「文末の音(ending_sound)」を抽出する
2. 直前の発言のending_soundと、今回の発言の先頭の音がつながっているか確認する(つながっていない場合の扱いは、単語しりとりほど厳密にする必要はなく、AIの応答生成側で吸収する想定。ユーザー入力についても致命的エラーにはせず、会話として自然に受け流す設計を基本方針とする)
3. ending_soundが「ん」の場合 → チェーン終了(`ended_by_n`)
4. 発言内容が過去の発言と完全一致する場合 → チェーン終了(`ended_by_duplicate`)
5. 上記いずれにも該当しなければ継続
