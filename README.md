# AI-shiritori-app

ブラウザで遊べるしりとりWebアプリ。ソロプレイ・AI対戦・文章しりとり(フリートーク)の3モードを搭載する。

詳細な仕様は [`docs/DESIGN.md`](docs/DESIGN.md)(設計書)、[`docs/USAGE.md`](docs/USAGE.md)(ユーザーマニュアル)を参照。

本リポジトリは [jig.jp サマーインターンシップ2026選考課題](https://jigintern.github.io/summer-2026-assignment/) のベース実装([`shiritori-app`](../shiritori-app))を拡張した「課題解答版(発展版)」。

## AIの活用について

本プロジェクトは実装のほぼ全工程でClaude Code(CLI)を活用している。具体的な活用箇所は以下の通り(実装が進むごとに追記していく)。

- 仕様書(`docs/DESIGN.md`)・使用書(`docs/USAGE.md`)の読解と、要件が曖昧な箇所(パスワード再設定方式・メール送受信方式・デプロイ先など)についての壁打ち・要件確定の対話
- 決定した要件に合わせた`docs/DESIGN.md`の追記・修正(管理者承認によるパスワード再設定フロー、デプロイ先の追記など)
- GitHubリポジトリ作成・初回コミット・push(`gh` CLI経由)
- プロジェクト全体のディレクトリ構成・`docker-compose.yml`・各`Dockerfile`・`.env.example`・`.gitignore`の設計と作成
- PostgreSQLのテーブル設計とマイグレーションファイル(`backend/migrations/`)の作成、および実際にDockerコンテナ上のPostgreSQLに対してマイグレーションのup/down動作を検証
- バックエンド(Go)の実装: 認証(JWT発行・検証、bcryptハッシュ)、ユーザー設定、パスワード再設定(管理者承認フロー)、REST APIサーバー(chi)一式
- パスワード再設定の管理者承認フロー(SMTP送信・IMAPポーリング)の実装。実際にテスト用のGmailアカウントを使ってend-to-endで動作検証しながら、以下の不具合をAIが自ら発見・診断・修正した
  - 当初採用したgo-imap v2(IMAP4rev2向け、開発中のベータ版)がGmail(IMAP4rev1)との相性で接続エラーを起こしたため、実績のあるgo-imap v1に切り替え
  - IMAPで取得した返信メール本文がMIME生データ(base64エンコードされたmultipart構造)のままで「空メールかどうか」を誤判定していた問題を、MIMEパーサーで`text/plain`部分を正しくデコードするよう修正
  - Gmailが返信メール自体を自動的に既読にしてしまい、未読ベースの検索だと見逃す場合があったため、アプリ専用のカスタムIMAPフラグで処理済み管理する方式に変更
  - Gmail返信時に自動付与される引用文(「〜さんは書きました:」+`>`引用ブロック)を「空メール」判定から正しく除外するロジックを追加
- 上記の検証中、作業終盤の後片付けコマンドでユーザーが設定した本番用`.env`を誤って削除してしまうミスがあった(ユーザー側にバックアップがあり実害なし)。AIが自らミスを申告し、原因と再発防止策を明示した
- しりとり判定モジュール(`internal/shiritori`)・文章しりとり判定モジュール(`internal/sentence`)の実装。kagome形態素解析ライブラリのAPIを実際にソースコードを読んで確認しながら実装し、設計書の具体例(「コーヒー」→「ひ」等)を含むユニットテストで検証
- Gemini API連携(`internal/gemini`)の実装。実際のAPIキーで結合テストを実行し、`gemini-2.5-flash`が新規アカウントでは404になることを発見、ユーザーの助言で`gemini-3.5-flash`に変更して解決
- ゲームセッション管理・REST API(`internal/game`)の実装。実際にサーバーを起動しAPIを叩いてend-to-endで検証する過程で、以下の不具合をAIが自ら発見・診断・修正した
  - AI対戦モードでGeminiに伝える「次の単語が続くべき音」を直前の単語の先頭音にしてしまっていたバグ(正しくは末尾音)
  - 「っ」(促音)を「ゃ・ゅ・ょ」(拗音)と同様に直前の文字と結合して扱っていたため、「ごりら」→「らっぱ」のような一般的なしりとりが成立しなかった問題(ユーザー指摘により発覚し、促音は独立した1モーラとして扱うよう修正。DESIGN.md 1章も更新)
  - 文末の句読点除去リストで全角の「！」「？」を書き忘れ(半角を誤って重複記載)、文末に記号が残るバグ
  - 上記を機に、モード3の文末音抽出方式をユーザー指示で「末尾から削る」方式から「末尾から遡ってひらがな/カタカナ/半角・全角英字を探す」方式に変更。モード1/2の入力・AI応答もひらがな/カタカナのみに制限する仕様に変更した
  - 非致命的エラー(辞書に無い語・不正な文字種)の理由をAPIレスポンスで`word_not_found`に決め打ちしていたハンドラーのバグ

いずれも、要件が曖昧な部分は実装前にユーザーへ確認を取りながら進めており、AIが独断で仕様を決めた箇所はない。また、AI自身の実装ミス・診断過程も含め、都度検証しながら進めている。

## 技術スタック

- フロントエンド: Next.js (React) + TypeScript
- バックエンド: Go
- データベース: PostgreSQL
- 外部AI API: Google Gemini API
- ローカル開発: Docker Compose (frontend/backend/postgresを一括起動)
- デプロイ先: [Railway](https://railway.app/) (Dockerfileベースでbackend/frontend/PostgreSQLをまとめてデプロイ)

## セットアップ

1. `.env.example` をコピーして `.env` を作成し、実際の値を設定する(APIキーやメール認証情報はコミットしないこと)

   ```
   cp .env.example .env
   ```

2. postgresのみ起動する(backend/frontend実装前の現段階)

   ```
   docker-compose up -d postgres
   ```

3. マイグレーションを適用する(要 [golang-migrate](https://github.com/golang-migrate/migrate) CLI。`brew install golang-migrate`)

   ```
   migrate -path backend/migrations -database "postgres://shiritori:shiritori@localhost:5432/shiritori?sslmode=disable" up
   ```

   ロールバックする場合は `down` を使う(全て戻す場合は `down -all`)。

4. backend/frontendの実装が揃ったら、以下で全サービスを一括起動する

   ```
   docker-compose up
   ```

   - frontend: http://localhost:3000
   - backend: http://localhost:8080
   - postgres: localhost:5432

> 現時点ではbackend/frontendの実装がまだなく、`docker-compose up`(postgres以外を含む一括起動)はビルドに失敗する。実装が進み次第、このREADMEも更新する。

## パスワード再設定の設計について

### 採用した方式: 管理者承認フロー

一般的な「メール内のトークン付きリンクをユーザー自身が踏んで新パスワードを設定する」方式ではなく、以下の**管理者承認フロー**を採用する。

1. ユーザーがログイン画面からパスワード再設定を申請する(メールアドレスを入力)
2. バックエンドが管理者宛(`ADMIN_EMAIL`)に、対象ユーザーのメールアドレスと申請ID(`request_id`)を含む通知メールを送信する
3. 管理者はメール内容を確認し、問題なければ**そのメールに本文を空にして返信する**ことで承認する
4. バックエンドが管理者のメールボックスをIMAPで定期的にポーリングし、件名・スレッド情報(`request_id`)から該当の申請を特定、本文が空であることを確認する
5. 確認が取れたら、ランダムな新パスワードを自動生成してハッシュ化保存し、ユーザーの登録済みメールアドレス宛に新パスワードを送信する

### なぜこの方式にしたか

- 個人開発・小規模運用のプロジェクトであり、管理者(開発者本人)が全ての再設定申請を目視確認できる規模である
- ユーザーが自分でパスワードを再設定できる方式(トークンリンク)よりも、悪意あるアカウント乗っ取り試行に対して人間の目によるチェックを1段挟める、という考え方
- 実装コストを抑えつつ、メール送受信(SMTP/IMAP)という技術要素を実際に触ってみたい、という学習目的も兼ねる

### 既知のセキュリティ上の弱点

- **メール返信の詐称可能性**: 標準的なSMTP/IMAPには送信者の強固な認証機構がない(SPF/DKIM/DMARCで一定の対策は可能だが完全ではない)。理論上は管理者のメールアドレスを詐称した返信が承認として扱われてしまうリスクがある
- **二要素認証なし**: 管理者側の承認操作(空メール返信)自体に、パスワードや追加の確認コードなどの二要素的な確認は設けていない
- **可用性への依存**: 管理者がメールを確認できない状況(旅行中・体調不良等)では、ユーザーはパスワード再設定を待たされる。運用でカバーする前提

これらは「本格的な複数ユーザー・商用サービスでは採用すべきでない」設計であることを認識した上で、今回はスコープと開発コストのバランスを優先し、意図的に許容している。

### 今後の展望(改善案)

- 管理者への通知メールに、承認用の一意なURL(ワンタイムトークン付き)を含め、空メール返信ではなくボタンクリックによる承認に変える(メール詐称耐性が上がる)
- 管理者承認に加えて、ユーザー側にも確認コード入力などの二要素的な確認ステップを追加する
- SPF/DKIM/DMARCの設定、または管理者からの返信元アドレス・Message-IDの厳密な検証を追加する
- 申請から一定時間(`expires_at`)経過した申請は自動的に`expired`にし、古い申請が誤って承認されないようにする(設計自体には`password_reset_requests.expires_at`として組み込み済み)
- 利用者数が増えた場合は、この方式自体を見直し、一般的なトークンリンク方式やOAuthログインへの移行を検討する
