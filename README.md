# AI-shiritori-app

ブラウザで遊べるしりとりWebアプリ。ソロプレイ・AI対戦・文章しりとり(フリートーク)の3モードを搭載する。

詳細な仕様は [`docs/DESIGN.md`](docs/DESIGN.md)(設計書)、[`docs/USAGE.md`](docs/USAGE.md)(ユーザーマニュアル)を参照。

本リポジトリは [jig.jp サマーインターンシップ2026選考課題](https://jigintern.github.io/summer-2026-assignment/) のベース実装([`shiritori-app`](../shiritori-app))を拡張した「課題解答版(発展版)」。

## デプロイ先

- **フロントエンド(動作確認用)**: https://frontend-production-ebe1.up.railway.app
- バックエンドAPI: https://backend-production-25353.up.railway.app

ログイン画面の「アカウントを作成する」から新規にメールアドレス・パスワードを登録して動作確認できる。

## 実装した機能

### ゲームモード

- **ソロプレイ**: 一人で単語をつなげ続けるモード。辞書に存在しない語は致命的エラーにせず再入力させ、「ん」で終わる語・重複語でゲームオーバーになる。入力欄には次に入力すべき音のヒント(ひらがな・カタカナ両方)を表示する。
- **AI対戦**: プレイヤーとAIが交互に単語を出し合う対戦モード。AI側はGemini APIを使わず、IPADIC辞書からのランダム選択と難易度別の「わざと失敗する確率」で強さを調整している(具体的な難易度アルゴリズムはあえて伏せているので、実際にプレイして体感してほしい)。
- **フリートーク(文章しりとり)**: 単語ではなく文章単位で、AIと日常会話をしながらしりとりのように文をつなげていくモード。文末の音は句読点・記号・漢字を無視してひらがな/カタカナ/英字まで遡って抽出する。AIが応答を生成している間は「考え中」インジケーターを表示する。

### 認証・アカウント

- メールアドレス+パスワードによる新規登録・ログイン・ログアウト(JWTアクセストークン+リフレッシュトークン)
- パスワード再設定は独自の**管理者承認フロー**(詳細は本ファイル下部のセクション参照)

### その他

- ダッシュボードに3モード共通のルールと各モードの説明を掲載
- 過去のプレイ履歴の一覧・詳細閲覧
- 設定画面(モード2のデフォルト難易度、モード3の会話トーンを保存)

より詳細な仕様・設計判断は [`docs/DESIGN.md`](docs/DESIGN.md)(設計書)、画面ごとの遊び方は [`docs/USAGE.md`](docs/USAGE.md)(ユーザーマニュアル)を参照。

## AIの活用について

本プロジェクトは実装のほぼ全工程でClaude Code(CLI)を活用している。具体的な活用箇所は以下の通り(実装が進むごとに追記していく)。

- 仕様書(`docs/DESIGN.md`)・使用書(`docs/USAGE.md`)の読解と、要件が曖昧な箇所(パスワード再設定方式・メール送受信方式・デプロイ先など)についての壁打ち・要件確定の対話
- 決定した要件に合わせた`docs/DESIGN.md`の追記・修正(管理者承認によるパスワード再設定フロー、デプロイ先の追記など)
- GitHubリポジトリ作成・初回コミット・push(`gh` CLI経由)
- プロジェクト全体のディレクトリ構成・`docker-compose.yml`・各`Dockerfile`・`.env.example`・`.gitignore`の設計と作成
- PostgreSQLのテーブル設計とマイグレーションファイル(`backend/migrations/`)の作成、および実際にDockerコンテナ上のPostgreSQLに対してマイグレーションのup/down動作を検証
- バックエンド(Go)の実装: 認証(JWT発行・検証、bcryptハッシュ)、ユーザー設定、パスワード再設定(管理者承認フロー)、REST APIサーバー(chi)一式
- パスワード再設定の管理者承認フロー(SMTP送信・IMAPポーリング)の実装。実際にテスト用のGmailアカウントを使ってend-to-endで動作検証しながら、以下の不具合をAIが自ら発見・診断・修正した
  - 当初採用したgo-imap v2(IMAP4rev2向け、開発中のベータ版)がGmail(IMAP4rev1)との相性で接続エラーを起こしたため、実績のあるgo-imap v1に切り替え
  - IMAPで取得した返信メール本文がMIME生データ(base64エンコードされたmultipart構造)のままで「空メールかどうか」を誤判定していた問題を、MIMEパーサーで`text/plain`部分を正しくデコードするよう修正
  - Gmailが返信メール自体を自動的に既読にしてしまい、未読ベースの検索だと見逃す場合があったため、アプリ専用のカスタムIMAPフラグで処理済み管理する方式に変更
  - Gmail返信時に自動付与される引用文(「〜さんは書きました:」+`>`引用ブロック)を「空メール」判定から正しく除外するロジックを追加
- 上記の検証中、作業終盤の後片付けコマンドでユーザーが設定した本番用`.env`を誤って削除してしまうミスがあった(ユーザー側にバックアップがあり実害なし)。AIが自らミスを申告し、原因と再発防止策を明示した
- しりとり判定モジュール(`internal/shiritori`)・文章しりとり判定モジュール(`internal/sentence`)の実装。kagome形態素解析ライブラリのAPIを実際にソースコードを読んで確認しながら実装し、設計書の具体例(「コーヒー」→「ひ」等)を含むユニットテストで検証
- Gemini API連携(`internal/gemini`)の実装。実際のAPIキーで結合テストを実行し、`gemini-2.5-flash`が新規アカウントでは404になることを発見、ユーザーの助言で`gemini-3.5-flash`に変更して解決
- ゲームセッション管理・REST API(`internal/game`)の実装。実際にサーバーを起動しAPIを叩いてend-to-endで検証する過程で、以下の不具合をAIが自ら発見・診断・修正した
  - AI対戦モードでGeminiに伝える「次の単語が続くべき音」を直前の単語の先頭音にしてしまっていたバグ(正しくは末尾音)
  - 「っ」(促音)を「ゃ・ゅ・ょ」(拗音)と同様に直前の文字と結合して扱っていたため、「ごりら」→「らっぱ」のような一般的なしりとりが成立しなかった問題(ユーザー指摘により発覚し、促音は独立した1モーラとして扱うよう修正。DESIGN.md 1章も更新)
  - 文末の句読点除去リストで全角の「！」「？」を書き忘れ(半角を誤って重複記載)、文末に記号が残るバグ
  - 上記を機に、モード3の文末音抽出方式をユーザー指示で「末尾から削る」方式から「末尾から遡ってひらがな/カタカナ/半角・全角英字を探す」方式に変更。モード1/2の入力・AI応答もひらがな/カタカナのみに制限する仕様に変更した
  - 非致命的エラー(辞書に無い語・不正な文字種)の理由をAPIレスポンスで`word_not_found`に決め打ちしていたハンドラーのバグ
- フロントエンド(Next.js 16 + TypeScript + Tailwind CSS)の実装。ログイン/新規登録/パスワード再設定申請、ダッシュボード、設定、ソロプレイ/AI対戦/フリートークの各プレイ画面、履歴一覧・詳細まで一式。scaffold(`create-next-app`)されたプロジェクトが「このNext.jsバージョンは学習データと異なる可能性がある」という警告(`AGENTS.md`)を出していたため、実装前に`node_modules/next/dist/docs/`配下のApp Routerドキュメントを実際に読んで最新のAPIを確認した
- ブラウザ操作ツール(claude-in-chrome)を使って実際に一通りの画面遷移(登録→ログイン→ダッシュボード→各プレイ画面→履歴)を操作し、以下の不具合をAIが自ら発見・診断・修正した
  - バックエンド(Go)にCORS設定が無く、ブラウザからのAPI呼び出しが全てブロックされていた問題(`go-chi/cors`を追加し、`FRONTEND_ORIGIN`環境変数で許可オリジンを設定できるようにした)
- UI/UXの大幅な見直し。shadcn/ui + lucide-reactを導入してアイコン化・コンポーネント統一を行い、ユーザーが持っていた別プロジェクト(社内の別案件のNext.jsフロントエンド)のログイン画面・ダッシュボードのデザインパターンを参考に、余白やレイアウトを作り直した(見た目のみ参考にし、そのプロジェクト固有の内容はコピーしていない)
- モード2(AI対戦)をGemini API不使用の辞書ベース方式に全面変更。Gemini経由だとAIが接続に失敗しやすくしりとりがすぐ終わってしまうという指摘を受け、IPADIC辞書(kagome-dict)の全名詞エントリを起動時に読み仮名の先頭モーラ別に索引化する`internal/shiritori.RandomWord`を新規実装。kagomeの内部データ構造(Morphs/Contents/POSTable)を実際にソースコードを読んで解析し、約23万語の名詞索引を約25msで構築できることをプロトタイプで確認してから実装した
- モード3(文章しりとり)が「全く応答が返ってこない」という報告を受け、実際に再現テストして原因を調査したところ、Gemini APIのタイムアウトが5秒に設定されていたのに対し会話履歴付きの応答生成が5秒を超えることが多く、`context deadline exceeded`で毎回失敗していたことが判明。タイムアウトを20秒に延長し、システムプロンプトもトーン別に整理して改善した
- ユーザーの指示で、50アカウントを作成しログイン/ログアウトを確認、各ゲームモードを50回ずつプレイする大規模な自動テスト(ソースコード変更・新規インストールは禁止という制約付き)を実施。ping-pong方式(2つのvs_aiセッションを互いのAI応答で駆動する)で50ラリー継続するチェーンを生成してモード1を検証、モード2は各難易度での勝利、モード3は10ラリーの会話成立を検証した。見つかった問題はGitHubのIssueにまとめ([#1](https://github.com/KaichoHarry/AI-shiritori-app/issues/1))、以下の修正を行った
  - **モード3の信頼性低下**: 大量テストでGemini API(`gemini-3.5-flash`)が503(高負荷)・504(タイムアウト)・429(レート制限)を高い頻度で返すことが判明(逐次10回のテストで成功率3/10)。一時的なエラーに対して最大3回まで自動再試行する仕組み(`internal/gemini.withRetry`)を追加し、タイムアウトも1回あたり15秒に調整した結果、同条件で10/10成功に改善した
  - **辞書チェックの不整合**: 「花火」はkagomeのトークナイザでKnown=trueになる一方、その読みの「はなび」をひらがなのままトークン化すると未知語判定になる不整合、およびひらがな⇔カタカナ変換フォールバックの副作用で「ぁ」「っ」等の小さい仮名1文字がIPADIC辞書内の記号的なエントリを拾って誤って既知語判定されるバグを発見。プレイヤー入力側の辞書チェックとAI側の単語生成を同一の読み索引データソースに統一して修正した(ユーザーからの追加指示で、小さい仮名は「ぁ」「っ」だけでなく20種類(ぁぃぅぇぉ等のひらがな・カタカナ計20文字)すべてをテストで網羅した)
  - ユーザーからの指摘で発覚した「もう一度遊ぶ」ボタンの不具合(Next.jsの同一ルートへの`Link`遷移では、既にそのルートを表示中だとコンポーネントが再マウントされず、古いセッションの画面が残ってしまう)を、ページ遷移ではなくクライアント側でセッション状態をリセットして再作成する方式に変更して修正した
  - ユーザーからの指摘で、外来語表記の小さい母音(ぁ・ぃ・ぅ・ぇ・ぉ。「ティ・ディ・ファ・フィ・フェ・フォ・チェ・シェ・ジェ」等)が拗音(ゃゅょ)と違って直前の文字に結合されず独立した1モーラとして扱われていたため、「カフェ」のように次の音が「ぇ」という他の単語がほぼ存在しない音になり、相手が絶対に返せない「最強」の単語が作れてしまう不具合を発見。拗音と同様に直前の文字と結合するよう修正した
- ユーザーからの指示で、モード1・2・3すべてに「次に入力(発言)すべき音」をひらがな・カタカナ両方で示すヒントUIを追加(`next_hint`フィールド)。あわせて、モード3のAI応答生成中は画面が止まって見える(フリーズしたように感じる)という指摘を受け、「AIが返事を考えています」という文言とアニメーションする3つの点による思考中インジケーターを追加した
- ダッシュボード画面に、3モード共通のしりとりルールと各モードの説明を追加。ユーザーからの指示で、AI対戦の難易度アルゴリズムの詳細は「エンタメ性を損なう」ため意図的に伏せ、フリートーク(モード3)は他モードとルールが異なり分かりにくいため、文末が句読点・記号・漢字で終わった場合の扱いなどを詳しく説明する内容にした
- ユーザーの指示で、Railway CLI(`railway config`によるInfrastructure as Code)を使って本番デプロイ作業を代行した。GitHubリポジトリ連携、Postgres/backend/frontendの3サービス作成、環境変数設定、公開ドメイン発行までを実施し、`.railway/railway.ts`にインフラ構成をコード化してコミットした。ただし、APIキー・パスワード・JWTシークレットなどの秘密情報はAIが代わりに入力しない方針を徹底し、`GEMINI_API_KEY`やSMTP/IMAPの認証情報、GitHub Appの認可操作はユーザー自身に行ってもらった(JWT署名用のシークレットのみ、外部アカウントに紐づかないアプリ内部の値のためAIが生成)。実際のデプロイ作業を通じて、ローカルでは表面化していなかった以下の不具合をAIが自ら発見・診断・修正した
  - `frontend/public`ディレクトリがローカルには存在するが中身が空でGitに追跡されておらず、GitHub上のリポジトリには存在しないため、Dockerfileの`COPY --from=builder /app/public`が失敗しビルドが落ちていた問題(`.gitkeep`を追加して解消)
  - `NEXT_PUBLIC_API_BASE_URL`はNext.jsのビルド時に静的に埋め込まれる値であるにもかかわらず、`frontend/Dockerfile`にも`docker-compose.yml`にもビルド時の`ARG`/`build.args`として渡す設定がなく(`docker-compose.yml`側は実行時の`environment`にしか設定されておらず無効だった)、本番ビルドがフォールバック値の`http://localhost:8080`を埋め込んでしまっていた問題。ユーザーが本番のログイン画面で「他のアプリやサービスへのアクセス許可」を求めるChromeのダイアログが出ると報告してくれたことが、公開サイトがローカルアドレスへ接続しようとしている(=バグの症状)と気づく決め手になった

いずれも、要件が曖昧な部分は実装前にユーザーへ確認を取りながら進めており、AIが独断で仕様を決めた箇所はない。また、AI自身の実装ミス・診断過程も含め、都度検証しながら進めている。

## セットアップ

1. `.env.example` をコピーして `.env` を作成し、実際の値を設定する(APIキーやメール認証情報はコミットしないこと)

   ```
   cp .env.example .env
   ```

2. postgresを起動する

   ```
   docker-compose up -d postgres
   ```

3. マイグレーションを適用する(要 [golang-migrate](https://github.com/golang-migrate/migrate) CLI。`brew install golang-migrate`)

   ```
   migrate -path backend/migrations -database "postgres://shiritori:shiritori@localhost:5432/shiritori?sslmode=disable" up
   ```

   ロールバックする場合は `down` を使う(全て戻す場合は `down -all`)。

4. ローカルでbackend/frontendをそれぞれ直接起動して開発する場合

   ```
   # backend (http://localhost:8080)
   cd backend && go run ./cmd/server

   # frontend (http://localhost:3000、別ターミナルで)
   cd frontend && npm install && npm run dev
   ```

5. Dockerで全サービスを一括起動する場合

   ```
   docker-compose up
   ```

   - frontend: http://localhost:3000
   - backend: http://localhost:8080
   - postgres: localhost:5432

## パスワード再設定の設計について

### 採用した方式: 管理者承認フロー

一般的な「メール内のトークン付きリンクをユーザー自身が踏んで新パスワードを設定する」方式ではなく、以下の**管理者承認フロー**を採用する。

1. ユーザーがログイン画面からパスワード再設定を申請する(メールアドレスを入力)
2. バックエンドが管理者宛(`ADMIN_EMAIL`)に、対象ユーザーのメールアドレスと申請ID(`request_id`)を含む通知メールを送信する
3. 管理者はメール内容を確認し、問題なければ**そのメールに本文を空にして返信する**ことで承認する
4. バックエンドが管理者のメールボックスをIMAPで定期的にポーリングし、件名・スレッド情報(`request_id`)から該当の申請を特定、本文が空であることを確認する
5. 確認が取れたら、ランダムな新パスワードを自動生成してハッシュ化保存し、ユーザーの登録済みメールアドレス宛に新パスワードを送信する

### なぜこの方式にしたか

- 個人開発・小規模運用のプロジェクトであり、管理者(開発者本人)が全ての再設定申請を目視確認できる規模である
- ユーザーが自分でパスワードを再設定できる方式(トークンリンク)よりも、悪意あるアカウント乗っ取り試行に対して人間の目によるチェックを1段挟める、という考え方
- 実装コストを抑えつつ、メール送受信(SMTP/IMAP)という技術要素を実際に触ってみたい、という学習目的も兼ねる

### 既知のセキュリティ上の弱点

- **メール返信の詐称可能性**: 標準的なSMTP/IMAPには送信者の強固な認証機構がない(SPF/DKIM/DMARCで一定の対策は可能だが完全ではない)。理論上は管理者のメールアドレスを詐称した返信が承認として扱われてしまうリスクがある
- **二要素認証なし**: 管理者側の承認操作(空メール返信)自体に、パスワードや追加の確認コードなどの二要素的な確認は設けていない
- **可用性への依存**: 管理者がメールを確認できない状況(旅行中・体調不良等)では、ユーザーはパスワード再設定を待たされる。運用でカバーする前提

これらは「本格的な複数ユーザー・商用サービスでは採用すべきでない」設計であることを認識した上で、今回はスコープと開発コストのバランスを優先し、意図的に許容している。

### 今後の展望(改善案)

- 管理者への通知メールに、承認用の一意なURL(ワンタイムトークン付き)を含め、空メール返信ではなくボタンクリックによる承認に変える(メール詐称耐性が上がる)
- 管理者承認に加えて、ユーザー側にも確認コード入力などの二要素的な確認ステップを追加する
- SPF/DKIM/DMARCの設定、または管理者からの返信元アドレス・Message-IDの厳密な検証を追加する
- 申請から一定時間(`expires_at`)経過した申請は自動的に`expired`にし、古い申請が誤って承認されないようにする(設計自体には`password_reset_requests.expires_at`として組み込み済み)
- 利用者数が増えた場合は、この方式自体を見直し、一般的なトークンリンク方式やOAuthログインへの移行を検討する

### 実装状況

バックエンド実装済み(SMTP送信: `net/smtp`、IMAPポーリング: `go-imap` v1、MIMEパース: `go-message/mail`)。実際にテスト用のGmailアカウントを使ってend-to-endで動作検証済み(発見・修正した不具合は上の「AIの活用について」を参照)。
